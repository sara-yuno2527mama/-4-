# みらいプロジェクト（`/mirai`）保存設計 — 相談まとめ

**目的**: みらい事務局ダッシュボードで「何を保存するか」「どこに保存するか」を整理する  
**形式**: 相談・グリル（コード変更なし）  
**日付**: 2026年6月

---

## 1. 背景

`/mirai` は「みらいプロジェクト事務局」向けの業務ダッシュボード。  
現状は `dashboard.json` に全部入った **静的モック**。本番運用に向けて、データを **DB** と **リポジトリ（Git）** のどちらに置くかを決める必要がある。

---

## 2. 合意した運用の前提

| # | 論点 | 結論 |
|---|------|------|
| 1 | **誰が日々更新するか** | **事務局ペアのみ**。実行委員・他担当は閲覧中心 |
| 2 | **総務タスクの性質** | **都度追加・削除** あり（毎月同じ型紙ではない） |
| 3 | **翌月のタスク** | **前月コピーして微調整**（ゼロから作り直しではない） |
| 4 | **実行委員会の次第・議事録** | **1回＝次第＋議事録のセット**（詳細 **§11**）。次第は会議前が主・会議後の**加筆修正程度**は同レコード上書き可 |
| 5 | **骨格（領域・トラック・フェーズ）** | 初めて使う年度のため **年度中に変える可能性あり** |

---

## 3. 結論：2つの置き場の役割

### リポジトリ（Git）＝ プログラムの型と初期データ

**向いているもの**

- データ構造の定義（Zod スキーマ等）
- 開発・デモ用の初期 seed（サンプル JSON）
- 画面ラベル・表示ルールなど **コードと一緒に変えるもの**

**向いていないもの**

- チェックリストの完了 ☑
- タスクのステータス変更
- 次第の編集・確定

→ 日次・月次で変わるものを Git に入れると、commit が増えすぎて運用が回らない。

### DB（データベース）＝ 本番の正本（事務局ペアが触るもの）

**向いているもの**

- 月次タスク（追加・削除・ステータス・チェックリスト）
- 実行委員会の **次第＋議事録セット**（§11）
- **骨格（領域・トラック・フェーズ）** ← 初年度はここも DB

→ 事務局ペアが画面から直接更新する **すべての運用データ** の置き場。

---

## 4. データの置き場一覧

| データ | 置き場 | 変える人 | 変える頻度 |
|--------|--------|----------|------------|
| データ構造（スキーマ） | リポジトリ | 開発者 | 機能追加時 |
| 開発用サンプル JSON | リポジトリ | 開発者 | 開発時 |
| **領域・トラック・フェーズ** | **DB** | 事務局ペア | 初年度は月に数回あり得る |
| **月次タスク** | **DB** | 事務局ペア | 毎日〜毎月 |
| **チェックリストの完了状態** | **DB** | 事務局ペア | 毎日 |
| **実行委員会セット（次第＋議事録）** | **DB** | 事務局ペア | 会議前（次第）・会議後（議事録） |
| **過去の確定セット（seed 投入分）** | **DB**（初回 import 元はリポジトリ seed） | 事務局ペア | 参照中心・軽微修正のみ |

---

## 5. 運用の流れ（イメージ）

### 総務タスク（月次）

```
【DB】4月のタスク群
    ↓ 月末「翌月コピー」
【DB】5月のタスク群 ← 追加・削除・文言調整
    ↓ 日次更新
【DB】5月の確定状態（チェック・ステータス）
```

### 実行委員会：次第と議事録（§11 参照）

```
【SharePoint 等】Word/PDF … 書類の正本（次第・議事録）
【DB】1回分のセット … 構造化データ（議題・決定・宿題等）
    会議前：次第を入力
    会議後：議事録を同じ回に追記（今後はセットで残す）
    次第の加筆修正程度 → 同レコード上書き（§11.4）
```

詳細は **§11**。Phase 6（次第 UI 統合）の前提。

---

## 6. 初年度向けの方針

初めて使う年度は試行錯誤が起きるため、次を推奨。

1. **骨格も DB に置く** — トラック追加・フェーズ日付修正を Git PR なしでできるようにする
2. **変更ログを残す** — 「いつ・誰が・何を変えたか」を DB に記録
3. **年度末にスナップショット** — DB から JSON エクスポートし、来年の seed に使えるようにする
4. **設定 UI は最初から全部作らない** — トラック追加などは最小限の画面 or 開発者支援でも可

1年落ち着いたら、骨格だけリポジトリ固定に戻す選択も可能。

---

## 7. 覚え方（1行）

> **リポジトリ = プログラムの型と初期 seed**  
> **DB = 事務局ペアが触る本番データ（骨格も作業も）**

## 10. 別端末確定を受けた方針更新（2026-07）

Phase 3 後半（タイマー/実績/繰越）の相談で **「主とペアは別端末で、それぞれ自分の番組表を触る」** が確定。これを受けた更新。関連: [crosscut §18](./mirai-crosscut-schedule-design.md)。

### 10.1 帰結

- localStorage は **端末ローカル** → 別端末では主/ペアが互いのデータを見られず、設計の根幹（**主/ペア 2 枚**）が成立しない。
- よって **localStorage は開発・デモ専用に降格**。**DB は事務局展開前に必須（クリティカルパス）**。

### 10.2 repository 抽象（先に入れる）

- 運用データ（予定編集・実績・完了・繰越・当月設定）は **async な repository interface 越し**に読み書きする。
- 現在の `hooks/use-mirai-roster.ts`（`useSyncExternalStore` + localStorage 直読み）は、この抽象の **localStorage アダプタ**として作り替え。
- Phase 3 後半の UI/ロジックは抽象に対して書き、**localStorage / DB を差し替え可能**にする。

### 10.3 シーケンス（合意：抽象ファースト）

1. repository 抽象を導入（localStorage アダプタ）
2. Phase 3 後半の UX を localStorage で固める（**1 人分の検証**）
3. **DB アダプタ ＋ 最低限の書込ゲート**を実装
4. 事務局展開前に **DB へ切替**（以降 localStorage は開発専用）

### 10.4 識別・権限（軽量先行）

- 識別は端末ローカルの **「主/ペア」選択**（パスワードなし）。実績の帰属・編集対象の枚に使う。
- 編集は既定で **自分の枚（実績/タイマー/繰越）**、相手は閲覧。共有データ（締め日・当番・お弁当・休み・委員会）は両者編集可。軽量識別のため当面はソフト運用、強制は本格認証で。
- **§2（更新は事務局ペアのみ／実行委員は閲覧）を守る**ため、DB アダプタ投入時に **最低限の書込ゲート（共有トークン等）** を 1 枚。本格認証は次フェーズ。

### 10.5 プロトタイプ期の注意

- localStorage 期は **端末ごとに独立・同期なし**。真の主/ペア協働は **DB 投入後**に成立。プロトタイプで検証できるのは 1 人分の操作感まで。

## 11. 実行委員会：次第と議事録（2026-07 相談合意）

Phase 6（次第 UI 統合）の前提。**Word/PDF の正本** と **アプリ用の構造化データ** は二層で持つ。

### 11.1 用語

| 用語 | いつ | 中身の例 |
|------|------|----------|
| **次第** | **会議前**（配布・当日まで） | 議題リスト、概要 |
| **議事録** | **会議後** | 話した内容の整理、**決まったこと**、**宿題** |

**次第**＝「これから話すリスト」、**議事録**＝「話した結果の記録」。別物だが **1回の実行委員会（事前打合せ含む）につき1セット** として残す（今後の方針）。

### 11.2 置き場（二層）

| 層 | 置き場 | 役割 |
|----|--------|------|
| **書類の正本** | SharePoint / ファイルサーバ等 | Word/PDF の次第・議事録（正式保管） |
| **構造化データ** | **DB**（本番）／**リポジトリ seed**（DB 前） | 画面参照・昨年同月比較・検索用 |

```
Word/PDF（SharePoint）  … 書類としての正本
        ↕ 内容は対応するが、ファイル丸ごとは DB に入れない
DB / seed（shidaiRecords 等） … 議題・決定・宿題など項目ごと
```

- **いま（DB 前）**: 過去分・デモ用は `data/mirai/dashboard.json` の `shidaiRecords`（または `data/mirai/seeds/*.json`）に seed として投入
- **DB 接続後**: 同 JSON を初回 import → 以降は画面から DB のみ更新（seed は触らない）

### 11.3 1回分のデータモデル（概念）

**1レコード ＝ 1回の開催**（`yearMonth` + `heldOn` + `kind` で特定）。中身を二段に分ける:

```ts
committeeSession {
  id, yearMonth, heldOn, kind, title
  // ── 次第（会議前） ──
  agenda: string[]           // 議題
  summary?: string           // 概要（次第側）
  // ── 議事録（会議後・セットで残す） ──
  minutesSummary?: string  // 議事録本文（任意）
  decisions?: string[]       // 決まったこと
  homework?: string[]        // 宿題
}
```

実装時は既存 `miraiShidaiRecordSchema` / `miraiShidaiDraftSchema` をこの概念に合わせて整理する（Phase 6）。**draft**＝編集中の今月次第、**record**＝確定セット（過去参照用）。

### 11.4 編集ルール

| 対象 | 会議前 | 会議後 |
|------|--------|--------|
| **次第** | 通常どおり編集 | **加筆修正程度**（誤字・表記・1行の追記等）は **同レコード上書き** で可。会議後に次第を作り直す運用はしない |
| **議事録** | — | 会議後に追記（今後は **次第とセットで必ず残す** 方針） |

**重大な訂正**（議題の差し替え・内容の書き換え等、稀）:

- **訂正版を別レコード** として追加（旧版は残す）
- 軽微修正のたびに別レコードは作らない

任意で **変更ログ**（§6）に「いつ・誰が・何を直したか」を残すと、加筆修正の追跡に足りる。

### 11.5 過去データ

| パターン | 扱い |
|----------|------|
| 次第のみ残っている月 | seed/DB に **次第部分だけ** 投入してよい |
| 議事録（決定・宿題）もある月 | **同じ回** に議事録ブロックを足す |
| 今後 | 原則 **次第＋議事録のセット** で登録 |

### 11.6 Phase 6 への申し送り

- Pane3＝読む / Pane4＝書く：同一回の **次第（読む中心）** と **議事録（書く中心）** を UI でセット表示
- 確定した `committeeMeeting` 日程（crosscut §16.1）→ 次第準備のマイルストーンと連動
- 永続化は **DB**（storage §10 の repository/DB 方針に従う）。ローカル only にしない
